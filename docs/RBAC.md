# РОЛИ И ПРАВА ДОСТУПА (RBAC) — FitIntel Pro

Полное руководство: что это, зачем, как устроено и как этим пользоваться.

---

## 1. Что такое RBAC и зачем он нужен

**RBAC (Role-Based Access Control)** — модель доступа, в которой каждое действие
в системе защищено **правом (permission)**, а пользователь получает права не
напрямую, а через **роль**. Один пользователь — одна или несколько ролей,
роль — набор прав.

**Зачем это клубу:**

| Без RBAC | С RBAC |
|---|---|
| Любой, кто вошёл в программу, видит всё | Кассир видит кассу, но не видит зарплаты |
| Увольнение = ручной перебор «чего он мог» | Отобрали роль — доступ исчез мгновенно |
| «Кто удалил платёж?» — неизвестно | Каждое действие пишется в аудит с именем |
| Снять кассу может любой | Только бухгалтер/админ (403) |

**Две стены защиты:** помимо прав на данные (сервер отклоняет запрос без права —
«Нет прав: payments.create»), есть **матрица экранов**: кассир физически не видит
в меню «Бухгалтерию» и «Экспорт». Данные и интерфейс защищены независимо.

---

## 2. Базовые понятия

| Термин | Что это | Пример |
|---|---|---|
| **Permission (право)** | Атомарное разрешение на одно действие. Кодируется как `объект.действие` | `payments.create`, `clients.read`, `roles.manage` |
| **Role (роль)** | Именованный набор прав. Выдаётся пользователю | `cashier`, `manager`, `accountant` |
| **User ↔ Role** | Связь многие-ко-многим: у пользователя может быть несколько ролей, у роли — много пользователей | manager1 → [manager] |
| **Экран (screen)** | Пункт меню desktop. Видимость настраивается отдельно от прав | «Платежи», «Бухгалтерия» |
| **Guard (страж)** | Серверная проверка перед операцией: «можно ли выдать/снять право, удалить роль» | нельзя снять `system.admin` у роли admin |
| **Audit (аудит)** | Журнал: кто, когда, что сделал, до/после | «manager1 создал платёж 100 ₽» |

**Соглашение имён прав:** `объект.действие` — `payments.refund`, `users.delete`,
`access.override`. Действия: `create / read / update / delete / refund / manage /
emergency / override`. Если право не выдано — действие запрещено.

## 3. Роли системы (9 штук)

| Роль | Код | Для кого | Что типично может | Чего НЕ может |
|---|---|---|---|---|
| **Администратор** | `admin` | Руководитель клуба, старший админ | Почти всё (71 право): пользователи, роли, устройства, касса, отчёты | — (но не bypass как superadmin) |
| **Директор/Владелец** | `owner` | Собственник | `audit.read`, `users.delete` — контроль, без операционки | проведение платежей |
| **Менеджер** | `manager` | Администратор зала/продаж | Клиенты, абонементы, тарифы (10 прав). После настройки — платежи | снятие кассы, настройки системы |
| **Кассир/Ресепшен** | `cashier` | Работа на входе и кассе | `clients.*`, проведение и подтверждение платежей, входы/выходы | отчёты по ФОТ, экспорт данных, снятие кассы |
| **Бухгалтер** | `accountant` | Учёт | Бухгалтерия, отчёты (ОСВ, P&L), экспорт, **снятие кассы** (инкассация) | изменение тарифов, удаление пользователей |
| **Тренер** | `trainer` | Тренерский состав | Свои клиенты, расписание, тарифы (чтение) | касса, платежи, отчёты |
| **Клиент** | `client` | Личный кабинет (будущее) | Просмотр своих данных | всё операционное |
| **Поддержка** | `support` | Техподдержка вендора | `clients.read`, `subscriptions.read` — диагностика | любые изменения |
| **Устройство** | `device` | Служебные учётки (турникеты, терминалы) | Минимум для работы API СКУД | **не может получить критичные права** (guard запрещает) |

**SuperAdmin** — отдельная учётная запись (флаг `is_superuser`), а не роль.
Проходит любую проверку прав (bypass), редактировать её права нельзя —
защита от потери доступа. Входит по лицензионному ключу.

## 4. Как это работает под капотом

**Проверка каждого запроса:**
1. Desktop шлёт запрос с токеном (`Authorization: Bearer …`).
2. `get_current_user` проверяет токен и находит пользователя.
3. `require_permission("payments.create")` собирает права пользователя
   (все его роли → все права ролей) и ищет нужное. Нет — `403 «Нет прав: …»`.
4. Операция выполняется, в **audit** пишется запись: кто, что, до/после.

**Стражи (guards) — защита самой настройки:**
- нельзя снять критичное право (`system.admin`, `roles.manage`, `users.delete`)
  у системных ролей — иначе можно «запереть» систему;
- нельзя удалить последнюю роль с `system.admin`;
- нельзя выдать критичные права служебной роли `device`;
- удаление/изменение системной роли `admin` — с подтверждением и в аудит.

**Блокировки при входе:** 5 неверных паролей → учётка блокируется на 5 минут.
Ответ при неверном пароле — `401` (не 500). Сессия протухает → desktop
автоматически перелогинивается (refresh-токен).

## 5. Как пользоваться (инструкции)

### 5.1 Создать сотрудника и дать ему доступ
1. «Пользователи» → «Создать пользователя»: логин, **email в формате
   name@domain.ru** (обязателен и проверяется — без него сломается профиль),
   пароль (мин. 8), роль.
2. Экран «Экраны ролей»: отметьте, какие вкладки видит эта роль.
3. Сообщите сотруднику логин/пароль. При первом входе он может сменить пароль
   сам: **«Файл» → «🔑 Сменить пароль…»**.

### 5.2 Настроить, что роль может делать (матрица прав)
1. «Роли и права» → слева выберите роль → справа появятся **все права
   системы с галочками**.
2. Отметьте нужные (например, для manager: `payments.create/read/update`).
3. **«💾 Сохранить изменения»** — система сама посчитает разницу и применит
   (добавит/снимет). В строке статуса будет «Сохранено. Применено N».
4. Права действуют **мгновенно** — перезаход пользователя не нужен
   (проверка идёт на каждый запрос).

### 5.3 Уволили сотрудника
«Пользователи» → выбрать → «Удалить» (или деактивировать). Доступ исчезает
сразу. История его действий остаётся в «Истории» — для разбора инцидентов.

### 5.4 Снятие кассы (инкассация) — пример самой строгой операции
«Платежи» → «💵 Снятие кассы» доступно **только** ролям `accountant`/`admin`
и superadmin (проверка на сервере, 403 остальным). Операция обнуляет
«Остаток прошлых смен» и записывает, кто и когда снял — неудаляемо.

## 6. Типовые наборы для клуба (готовые рецепты)

| Позиция | Роль | Экраны (матрица) | Права |
|---|---|---|---|
| Кассир на входе | `cashier` | Главная, Клиенты, Абонементы, Входы/Выходы, Расписание, Платежи | clients.*, payments.create/read/update, visits.* |
| Администратор зала | `manager` | + Тарифы, Услуги | + tariffs.*, services.* |
| Бухгалтер | `accountant` | Бухгалтерия, Отчёты, Экспорт, Платежи (чтение) | accounting.*, reports.*, export.*, payments.read |
| Тренер | `trainer` | Главная, Расписание, Клиенты (чтение) | clients.read, schedule.* |
| Техподдержка вендора | `support` | Клиенты (чтение) | clients.read, subscriptions.read |

## 7. Безопасность: что важно знать владельцу

1. **Право — не подарок, а ответственность.** Каждое действие с деньгами,
   данными клиентов (152-ФЗ!) и настройками пишется в аудит с именем.
2. **Принцип минимума:** выдавайте ровно те права, которые нужны для работы.
   Лишнее — дыра. «На всякий случай admin» — плохая практика.
3. **Служебные учётки (`device`)** — только для оборудования, без критичных
   прав (сервер не даст выдать).
4. **Пароли:** минимум 8 символов; регулярная смена через «Файл → Сменить
   пароль»; superadmin держит пароль в недоступном месте (восстановление —
   только через разработчика).
5. **Email пользователя обязателен и валиден** — он используется в профиле
   и аудите; сервер отклонит `user@` или `name@local`-зоны.

## 8. Типичные проблемы и решения

| Симптом | Причина | Решение |
|---|---|---|
| «Нет прав: X» у пользователя | Права нет в его ролях | «Роли и права» → галочка → «💾 Сохранить» |
| «Недостаточно ролей» | Требуется admin, а вы manager | Войти под admin или выдать роль admin |
| 403 на «Снятие кассы» | Роль не accountant/admin | Так задумано — это защита денег |
| Экрана нет в меню | Не отмечен в «Экраны ролей» | Отметить там (это про видимость, не про права) |
| 500 при сохранении ролей | У сервера нет метода guard | Обновить сервер (фикс `check_can_add_permission_to_role`) |
| 500 после входа (/auth/me) | Кривой email пользователя | Email обязателен в формате name@domain.ru |
| «Смена пароля — Обязательно» | Временный пароль из письма | Введите старый (временный) и новый — окно закроется |

## 9. Архитектура (для разработчика)

- Таблицы: `roles`, `permissions`, `role_permissions` (связка),
  `user_roles`, `ui_role_screens` (матрица экранов), `audit_log` (все действия).
- Эндпоинты: `GET /roles/` (+права роли), `POST/DELETE /roles/{id}/permissions`,
  `GET/POST /users/…/roles/assign|revoke`, `GET /permissions/`,
  диагностика `GET /users/{id}/roles`, `GET /users/{id}/permissions`.
- Проверки: `require_permission` (права), `require_roles` (например, настройки
  кассы — admin), `RBACGuardService` (защита самих ролей), audit через
  `AuditService.log(action=..., actor_user_id=..., after_data={...})`.
- Bypass: `is_superuser=True` (superadmin) — через `require_permission`.
- Известные исторические дефекты (исправлено): выдача прав падала с 500
  (не было guard-метода на добавление); email не валидировался; импорт
  HTTPException отсутствовал в users.py.
