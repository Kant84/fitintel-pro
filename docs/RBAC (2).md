# РОЛИ И ПРАВА ДОСТУПА (RBAC) — FitIntel Pro

Справочник составлен **по реальному состоянию базы** (дамп `roles` /
`role_permissions` / `permissions` от 05.10.2026). Заводские наборы ниже —
это то, что действительно выдано сейчас. Меняется в «Роли и права».

---

## 0. Как читать

- **Право** — разрешение на одно действие, код `объект.действие`.
  Нет права → `403 «Нет прав: <код>»`.
- **Роль** — корзина прав. Выдаётся пользователю в «Пользователи».
  Проверка на каждый запрос → изменения применяются мгновенно.
- **Экраны** («Экраны ролей») — видимость меню, отдельно от прав.
- **Guard** — серверные запреты (нельзя снять `system.admin` у admin и т.п.).

---

## 1. superadmin (флаг is_superuser) — НЕ роль

**Для чего:** первичная настройка и аварийный доступ. Создаётся активацией
лицензии (логин/пароль из ключа FIPRO-…).

**Может:** всё — проходит любую проверку (bypass), включая «Снятие кассы»
без роли бухгалтера и правку самой роли admin.

**Правила:** пароль — в сейф, не для daily-работы; потеря = восстановление
через разработчика (License Studio).

---

## 2. admin — Администратор (71 право, реальный список)

**Назначение:** полное операционное управление клубом.

**Права по группам (факт):**
- **Доступ и пользователи:** `system.admin`, `access.override`,
  `access.cache.manage`, `roles.manage`, `roles.read`, `permissions.read`,
  `users.create/read/update/delete`, `audit.read`;
- **Клиенты и продажи:** `clients.create/read/update`, `subscriptions.
  create/read/update/cancel/freeze/renew/history`, `tariffs.create/read/
  update`, `services.create/read/update/delete`, `sales.create/read`,
  `wallet.deposit/read`, `documents.create/read/delete`;
- **Касса и деньги:** `payments.create/read/update/refund`, `cash_desk.open/
  close/read/manage`, `receipts.read/send`, `lockers.read/update/assign/
  manage` (**включая «Снятие кассы»**);
- **Клуб:** `credentials.create/read/update/delete`, `visits.create/read/
  update`, `face.read/manage`, `devices.create/read/update/delete`;
- **Настройки:** `club_settings.read/update`, `settings.read/update`,
  `setup.read/write`, `ui-config.read/update`.

**Чего НЕТ у admin (важно):** `reports.*`, `accounting.*`, `exports.*` —
соответствующие коды прав в этой базе не заведены; отчёты строятся из других
данных или через экраны, а проверка идёт по имеющимся правам. `visits.delete`
и `payments.delete` тоже отсутствуют — удаления визитов/платежей в системе
нет как операции (только отмена/возврат).

**Guard:** нельзя снять критичные права (`system.admin`, `roles.manage`,
`users.delete`) и удалить саму роль — страховка от «запирания» системы.

**Кому:** директор клуба / старший админ. Пароль — сложный, смена при
увольнении.

---

## 3. owner — Владелец (2 права)

`audit.read` + `users.delete`.

**Назначение:** контроль без операционки. Видит всю «Историю» (кто что
сделал — касса, удаления, смены паролей) и может удалить пользователя при
увольнении, но не может провести платёж, изменить тариф, пробить чек.
Разделение «собственник ≠ оператор» — база внутреннего контроля.

**Кому:** собственник бизнеса; в сети — контролёр франшизы.

---

## 4. manager — Менеджер (13 прав)

`clients.create/read/update`, `subscriptions.create/read/update`,
`tariffs.create/read/update`, `users.delete`,
`payments.create/read/update` *(добавлено настройкой 05.10.2026)*.

**Назначение:** продажи и оформление без доступа к деньгам «на вынос» и
настройкам. До добавления `payments.*` менеджер **не мог провести платёж**
(«Нет прав: payments.create») — сейчас может продавать с авто-чеком.

**Чего НЕ может:** снятие кассы (403), настройки кассы (`settings.update` —
admin), возвраты (нет `payments.refund`), экспорт, роли.

**⚠ Замечание:** заводское `users.delete` у manager спорно — менеджер может
удалить любую учётку. Рекомендуется снять галочкой в «Роли и права».

---

## 5. cashier — Кассир / Ресепшен (6 прав)

`clients.create/read`, `subscriptions.create/read/update`, `tariffs.read`.

**Назначение:** работа на входе и с клиентом. Заводского набора **хватает
только на оформление** — для реальной кассы нужно расширение:

**Рекомендуемое расширение:** `payments.create/read/update`,
`payments.refund` (возврат — отдельное право, защита от «дружеских
возвратов»), `visits.create/read`, `visits.update` (ручной вход/выход),
`receipts.read`.

**Сценарий:** продал абонемент → «Платежи»: провести → подтвердить → чек
на ККТ автоматически; смену открыл/закрыл по графику; возврат — только с
причиной и правом refund.

---

## 6. accountant — Бухгалтер (**0 прав — требуется настройка!**)

**Сейчас роль пустая:** в заводском сиде прав бухгалтеру не выдано. Учётная
запись с ролью accountant сможет войти, но любой запрос получит 403.

**Рекомендуемый набор (выдать в «Роли и права»):**
`payments.read`, `cash_desk.read`, `receipts.read`, `audit.read`,
`lockers.read` — сверка кассы и просмотр документов;
`subscriptions.read`, `clients.read` — проверка выручки по продажам.
Инкассация («Снятие кассы») — через роль admin либо отдельное расширение
(проверка на сервере принимает admin/superadmin/accountant).

**Сценарий после настройки:** ежедневная сверка Z-отчёт ↔ проводки ↔
выписка; инкассация; разбор расхождений по аудиту. Операционных прав
(создание платежей) у бухгалтера быть не должно.

---

## 7. trainer — Тренер (3 права)

`clients.read`, `subscriptions.read`, `tariffs.read` — только чтение.

**Назначение:** расписание и контекст клиента (действует ли абонемент,
остаток визитов) — для корректной тренировки. Ничего не создаёт, не меняет,
зарплату коллег не видит. Если тренер продаёт персоналки — выдать вторую
роль (cashier/manager), не расширять trainer.

---

## 8. support — Техподдержка (2 права)

`clients.read`, `subscriptions.read` — read-only диагностика на время
инцидента. Все просмотры в аудите. Учётка временная: выдал admin → решили
проблему → деактивировал.

---

## 9. client — Клиент (0 прав)

Роль-заготовка личного кабинета (будущее). Сейчас — маркер «это клиент, не
персонал». ЛК будет фильтровать данные по своему ID (права вида
`subscriptions.read` по своим записям).

---

## 10. device — Устройство (0 прав)

Служебная роль для железа (турникеты, терминалы, агенты). Прав выдаётся
минимум под конкретное устройство. **Guard:** критичные права
(`system.admin`, `roles.manage`, `users.*`) роли device **не выдать** —
утёкшая учётка турникета не даст управления системой.

---

## 11. Сводная картина и жизненный цикл

```
owner      — аудит + увольнения (контролёр)
admin      — всё операционное (71 право), включая инкассацию
accountant — учёт (набор выдать!), сверка, инкассация
manager    — продажи, клиенты, тарифы, платежи (настроенные)
cashier    — касса, входы (нужно расширить payments.*)
trainer    — read-only расписание
support    — временный read-only на инцидент
device     — служебный минимум, guard от повышения
```

**Цикл сотрудника:** наняли → пользователь + роль + экраны → работает →
сменил пароль сам («Файл → 🔑 Сменить пароль…») → уволили → учётку удалили
→ доступ исчез мгновенно, действия остались в «Истории».

---

## 12. Шпаргалка

| Ситуация | Решение |
|---|---|
| «Нет прав: X» | «Роли и права» → роль → галочка X → «💾 Сохранить» (применяется сразу) |
| Бухгалтер ничего не может | Выдать accountant набор из раздела 6 |
| Кассир не может продать | cashier + `payments.create/read/update` |
| Кассир не может вернуть деньги | cashier + `payments.refund` |
| Менеджер может удалять пользователей | Снять у manager галочку `users.delete` |
| «Снятие кассы» → 403 | Так задумано: только admin/accountant/superadmin |
| Экрана нет в меню | «Экраны ролей» — отметить (видимость ≠ права) |
| 500 при сохранении ролей | Обновить сервер (фикс guard `check_can_add_permission_to_role`) |
