## Портал не открывается (502/000)
Категория: server
Вариации запроса: портал не открывается, не грузится приложение, 502 у всех

**Пошагово.**
1. `docker compose ps` — контейнеры Up? api unhealthy первые 30 сек — подождать.
2. `curl -s http://127.0.0.1/api/v1/health/` → JSON?
3. Нет JSON: `docker compose logs --tail=100 api` — traceback (миграция? env? порт?).
4. БД: `docker compose ps db` — healthy? место на диске (`df -h`).
5. nginx: `docker compose logs nginx --tail=50` — upstream ошибки.
Маркер восстановления: health ok + desktop «Проверить связь» зелёный.

**Если не помогло:** Ескалация: «Помощь → Поддержка разработчика (MAX)».

## После обновления: цикл сбоя контейнеров
Категория: server
Вариации запроса: контейнер перезапускается, restart loop, up down постоянно

**Почему.** Ошибка при старте (миграция, env, зависимость БД) — контейнер падает и перезапускается.
**Пошагово.**
1. `docker compose ps` — статус Restarting?
2. `docker compose logs --tail=100 api` — первая ошибка в цикле (читайте с начала лога).
3. Типовые: миграция упала (текст ошибки — поддержке), неверный env (проверить .env vs шаблон), БД не готова (depends_on condition).
4. НЕ долбить `up -d` по кругу — это не лечит, лог растёт.
5. Временный откат: предыдущий образ (`docker tag` перед обновлением) + бэкап БД.

**Если не помогло:** Ескалация: «Помощь → Поддержка разработчика (MAX)».

## База раздувается/тормозит
Категория: server
Вариации запроса: база тормозит, запросы медленные, postgres медленный

**Пошагово.**
1. Размер: `docker compose exec db psql -U fitintel -c "SELECT pg_database_size('fitintel');"`
2. Топ таблиц: запрос к pg_stat_user_tables (n_dead_tup) — вакуум: `VACUUM (ANALYZE);` в часы низкой нагрузки.
3. Место на диске под WAL: `df -h` (pg_wal растёт при долгих транзакциях/репликации).
4. Медленные запросы: pg_stat_statements (если включён) — топ по времени.
5. Индексы: `REINDEX` при деградации (редко нужно).
Массовая чистка истории — статья data-routines «Очистка старых данных».

**Если не помогло:** Ескалация: «Помощь → Поддержка разработчика (MAX)».

## Redis отказал: что ломается
Категория: server
Вариации запроса: redis упал, celery не работает, кэш отказ

**Что ломается.** Фоновые задачи (celery: уведомления, дайджест, вебпуш), кэш/блокировки, SSE-подписки. API обычно живёт, но уведомления копятся.
**Пошагово.**
1. `docker compose ps redis` → `docker compose logs redis --tail=50`.
2. Перезапуск: `docker compose restart redis` → проверка worker'ов: `pgrep -f spawn_main` в celery-worker.
3. Не стартует: место на диске, memory limits.
4. Проверка: тестовое уведомление («Уведомления → Тест») ушло; дайджест по расписанию.
Потерянные задачи при долгом отказе — перезапуск beat: `docker compose restart celery-beat celery-worker`.

**Если не помогло:** Ескалация: «Помощь → Поддержка разработчика (MAX)».

## Нет места на диске: аварийный протокол
Категория: server
Вариации запроса: диск заполнен аварийно, no space left, что чистить срочно

**Срочный протокол.**
1. `df -h` — какой раздел.
2. Крупнейшие каталоги: `du -sh /var/lib/docker/* /opt/fitintel-pro/* 2>/dev/null | sort -rh | head`.
3. Освобождение по приоритету:
   - `journalctl --vacuum-size=100M` (логи systemd).
   - Старые образы: `docker images` → удалить старые теги fitintel.
   - Бэкапы: перенести свежие в offsite, старые удалить (ротация).
   - `docker system prune -a` (крайняя мера — пересборка потом).
4. Проверка: БД стартует (PostgreSQL падает при 0 места сразу).
5. Профилактика: мониторинг места (алерт >80%).

**Если не помогло:** Ескалация: «Помощь → Поддержка разработчика (MAX)».

## SSL-сертификат истёк
Категория: server
Вариации запроса: сертификат истёк, https ошибка, сертификат продлить

**Симптомы.** Браузер «соединение не защищено», webhook'и MAX/ЮKassa не доходят (они требуют валидный HTTPS).
**Пошагово.**
1. Срок: `echo | openssl s_client -connect <домен>:443 2>/dev/null | openssl x509 -noout -dates` (или в браузере).
2. Продление Let's Encrypt: certbot (если используется) — `certbot renew`; на платформе (125) — сертификаты в `/opt/fixintel/fixintel/ssl/<поддомен>/`.
3. Перезапуск nginx после замены: `docker compose restart nginx` (или контейнер фронта).
4. Проверка: `curl -sI https://<домен>` — 200/301, сертификат валиден.
5. Webhook'и: тестовый платёж ЮKassa/сообщение MAX — дошло.

**Если не помогло:** Ескалация: «Помощь → Поддержка разработчика (MAX)».

## Webhook'и не доходят (MAX/ЮKassa)
Категория: payments
Вариации запроса: webhook не приходит, юкасса не стучится, max webhook молчит

**Чек-лист.**
1. URL из кабинета правильный и доступен ИЗ ИНТЕРНЕТА: `curl -sI https://<домен>/api/v1/payments/yookassa/webhook` (не 404/000).
2. HTTPS валиден (см. сертификат) — иначе провайдер отказывается слать.
3. Firewall/nginx: путь проксируется на api (конфиг nginx клуба/фронта).
4. IP-лимиты: rate-limit не режет провайдера (whitelist IP ЮKassa — runbook; MAX — платформенные IP).
5. Логи api: `docker compose logs api | grep -i webhook` — запросы доходят? Ответы 200?
6. Кабинет провайдера: журнал webhook'ов (уходят ли, какие коды ответа).
Диагноз: не уходят (кабинет) → доступность/HTTPS; уходят, 200 → логика обработки (логи api).

**Если не помогло:** Ескалация: «Помощь → Поддержка разработчика (MAX)».

## Турникет отвалился вечером (диагностика)
Категория: skud-hardware
Вариации запроса: турникет перестал работать вечером, контроллер не отвечает

**Чек-лист (вечерний отказ — нагрузка/сеть/питание).**
1. Контроллер: питание (индикация), перезагрузка контроллера (кнопка/автомат).
2. Сеть: `ping <IP-контроллера>` с сервера; свитч порта; IP не сменился (DHCP-аренда истекла — закрепить статик).
3. ITCService: `systemctl status itcservice` → перезапуск; лог на 401 (пароль после ротации?).
4. API: curl checkaccess — 422 норма / 401 пароль / 000 API лёг.
5. Ручной режим: впуски из desktop до восстановления (регламент).
Маркер: тестовая карта проходит, визит в журнале.

**Если не помогло:** Ескалация: «Помощь → Поддержка разработчика (MAX)».

## ККТ перестала печатать чеки в смену
Категория: cash-fiscal

**Пошагово.**
1. «Платежи → ⚙ Настройки кассы → тестовый чек» — ошибка текстом.
2. Связь с ДТО: `ping <IP-ПК-кассы>`; браузер `http://<IP>:16732` — веб-интерфейс отвечает?
3. ДТО: служба ДТО запущена? ККТ включена/бумага/ФН (см. «Касса вернула ошибку: 1»).

5. Не чинится за 10 минут — регламент ФН: приостановить безналичные чеки, вызвать поддержку АТОЛ/ОФД, фиксировать ручные чеки (критично — кассовая дисциплина).

## Производительность: API медленный (>2 сек)
Категория: server
Вариации запроса: api медленный, долго грузит, тормозит программа

**Пошагово.**
1. Метрики: `/metrics` (Prometheus) — длительность запросов, топ медленных.
2. Нагрузка хоста: `top`/`htop` — CPU/RAM/IO (swap? iowait?).
3. БД: активные запросы `pg_stat_activity` — долгие транзакции; вакуум (статья «База тормозит»).
4. Точечно: какой экран тормозит → какой запрос (логи api access.log по времени) → индексы/фильтры.
5. Стенд: нагрузочный тест №1 показывал ~20 r/s на стенде 4 vCPU — сравните вашу нагрузку; апгрейд ресурсов при пределе.
6. Временно: перезапуск контейнеров очистит «зависшие» соединения.

**Если не помогло:** Ескалация: «Помощь → Поддержка разработчика (MAX)».

## Дата/время сбиты после перезагрузки
Категория: server
Вариации запроса: время сбивается, часы спешат после ребута, ntp не работает

**Почему.** NTP не настроен/блокируется, RTC батарейка села на железе.
**Пошагово.**
1. `timedatectl` — NTP enabled? синхронизировано?
2. Включить: `timedatectl set-ntp true`.
3. Проверить доступность NTP (123/udp) — файрвол.
4. Hyper-V/VM: синхронизация времени с хостом (integration services) — включить, иначе гость плывёт.
5. После коррекции: перезапуск контейнеров (JWT/планировщик).
Последствия сбитого времени: BadJwtToken (webpush), неверные время чеков/визитов, сбит дайджест.

**Если не помогло:** Ескалация: «Помощь → Поддержка разработчика (MAX)».

## Сервер подвергся подозрительной активности
Категория: server
Вариации запроса: взлом подозрение, подозрительные логины, безопасность инцидент

**Протокол.**
1. Изолировать: сменить пароли SSH/панелей, проверить `last`/`journalctl _COMM=sshd` — входы с неизвестных IP.
2. Проверить пользователей: `cat /etc/passwd | tail` (новые?), группа docker (лишние?), cron-задания.
3. Процессы: `htop` — посторонние процессы/майнеры.
4. Сетевые соединения: `ss -tlnp` — неизвестные listener'ы.
5. Секреты: ротация SECRET_KEY/ITC/SMTP/токенов (после компрометации), `up -d --force-recreate`.
6. Аудит FitIntel: «Аудит доступа» — действия с чужих учёток.
7. При подтверждении взлома — восстановление из чистого бэкапа на пересобранный сервер.

**Если не помогло:** Ескалация: «Помощь → Поддержка разработчика (MAX)».
