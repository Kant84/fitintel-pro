## Парольная политика клуба
Категория: users-rbac
Вариации запроса: парольная политика, требования пароля, смена паролей регламент
📷 Скриншоты: scr-set-20.png

**Политика (рекомендация).**
1. Минимум 8 символов, буквы+цифры (требование системы — 8+).
2. Уникальность: не использовать пароли от почты/других сервисов.
3. Смена: принудительно — при утечке/увольнении коллеги; планово — раз в 6–12 мес.
4. Временные пароли — сменить при первом входе (система сама требует).
5. Не хранить на бумажках/в чатах; менеджер паролей — только личный.
Контроль: аудит логинов; 5 неверных = блокировка 5 мин (защита от подбора).

**Если не помогло:** Ескалация: «Помощь → Поддержка разработчика (MAX)».

## Доступ уволенного: чек-лист закрытия
Категория: users-rbac
Вариации запроса: уволенный доступ закрыть, чек-лист увольнения, отозвать доступ
📷 Скриншоты: scr-set-20.png

**Чек-лист (в день увольнения).**
1. Деактивировать учётку («Пользователи → Деактивировать») — вход закрыт мгновенно.
2. Снять роли и экраны (карточка → «Роль и права»).
3. QR/браслет сотрудника — заблокировать («Браслеты/Карты → QR сотрудников»).
4. Пароль desktop на общих ПК — сменить, если сохранён («Запомнить меня»).
5. Service-аккаунты, которыми владел сотрудник — перевыпустить токены.
6. История действий — сохранена (аудит); доступ к документам — закрыт с деактивацией.

**Если не помогло:** Ескалация: «Помощь → Поддержка разработчика (MAX)».

## Общий ПК: правила безопасной работы
Категория: desktop
Вариации запроса: общий компьютер правила, выход из учётки, безопасность на общем пк
📷 Скриншоты: scr-set-20.png

**Правила.**
1. Выход в конце смены ОБЯЗАТЕЛЕН («Файл → Выход»; не сворачивать!).
2. «Запомнить меня» — не включать на общих ПК.
3. Пароль не сохранять в браузере/ПО.
4. Экран блокировать (Win+L) при отходе.
5. USB-носители — запрещены (вирусы/утечка данных).
6. Автовход Windows — только для киоск-режима с минимальными правами.
Контроль: администратор проверяет список активных сессий в аудите еженедельно.

**Если не помогло:** Ескалация: «Помощь → Поддержка разработчика (MAX)».

## Разделение доступа к деньгам (антиконфликт)
Категория: users-rbac
Вариации запроса: доступ к деньгам разделение, кто снимает кассу, контроль кассы
📷 Скриншоты: scr-set-20.png

**Принцип разделения.**
1. Кассир: платежи/подтверждения, но НЕ снятие кассы (только Бухгалтер/Администратор — системно 403 иначе).
2. Бухгалтер: снятие кассы, проводки, отчёты — но не изменение цен/тарифов.
3. Администратор: всё, но снятие кассы — тоже фиксируется (аудит!).
4. Двое при инкассации/пересчёте.
Контроль: журнал «Платежи», аудит снятий, X/Z-отчёты по сменам.

**Если не помогло:** Ескалация: «Помощь → Поддержка разработчика (MAX)».

## Фишинг и социальная инженерия для персонала
Категория: users-rbac
Вариации запроса: фишинг обучение, социальная инженерия, подозрительные письма
📷 Скриншоты: scr-set-20.png

**Правила для персонала.**
1. Пароли/коды — НИКОМУ: ни «техподдержке», ни «директору в отпуске» (проверяйте лично).
2. Письма со ссылками «срочно войдите» — не открывать; вход — только через свой ярлык/desktop.
3. USB от «клиента» — не втыкать (IT проверит).
4. Просьбы «перевести деньги/изменить реквизиты» — подтверждение по телефону по известному номеру.
5. Подозрительное — администратору/IT немедленно.
Обучение: 15 минут при онбординге + напоминание раз в квартал.

**Если не помогло:** Ескалация: «Помощь → Поддержка разработчика (MAX)».

## Резервные копии как элемент безопасности
Категория: server
Вариации запроса: бэкап безопасность, вымогатели защита, резервные копии рansomware
📷 Скриншоты: scr-set-20.png

**Угроза.** Вымогатели шифруют сервер + примонтированные диски; бэкап на том же сервере — тоже зашифруют.
**Защита.**
1. Offsite-копия (внешний носитель/другая машина) — обязательна; offsite_copy.sh.
2. Ротация: минимум 7 дневных копий; месячные — хранить 3–6 мес.
3. Доступ к бэкапам — отдельная учётка (не та же, что у админов сервера).
4. Тест восстановления ежемесячно (бэкап, который не восстанавливается, = нет бэкапа).
5. При атаке: изолировать сеть, НЕ платить сразу, восстановление из чистой копии + смена всех секретов.

**Если не помогло:** Ескалация: «Помощь → Поддержка разработчика (MAX)».

## Аудит доступа: что проверять еженедельно
Категория: users-rbac
Вариации запроса: аудит еженедельная проверка, что смотреть в аудите, контроль действий
📷 Скриншоты: scr-set-20.png

**Еженедельный чек-лист (администратор, 10 минут).**
1. Неудачные логины: пачки подряд = подбор пароля → сменить пароль пострадавшего, проверить IP.
2. Просмотры чувствительных данных: документы/лицензии — кто и зачем (вне рабочих задач — разговор).
3. Снятия кассы: суммы/время vs график инкассации.
4. Изменения прав/ролей: кто и кому (согласовано?).
5. Имперсонация поддержки: были ли сеансы (должны быть только по вашим обращениям).
6. Анонимизации/восстановления корзины — обоснование.
Экспорт аудита — в месячный отчёт владельцу.

**Если не помогло:** Ескалация: «Помощь → Поддержка разработчика (MAX)».

## Инцидент утечки персональных данных
Категория: processes
Вариации запроса: утечка пдн, инцидент персональных данных, что делать при утечке
📷 Скриншоты: scr-set-20.png

**Протокол.**
1. Сдержать: отозвать доступ (деактивация, смена паролей/токенов), заблокировать канал утечки (письмо/доступ).
2. Зафиксировать: аудит — что утекло, кто, когда; скриншоты/логи.
3. Оценить объём: список субъектов (клиенты/сотрудники), категории данных.
4. Уведомить: владелец/руководитель клуба; по требованиям закона — Роскомнадзор/субъекты (юрист клуба/владельца).
5. Предотвращение: причина (доступ? фишинг? общий ПК?) — устранить + обучение.
Не паниковать, не скрывать: документированное реагирование — ваша защита.

**Если не помогло:** Ескалация: «Помощь → Поддержка разработчика (MAX)».

## Безопасность интеграций (токены, ключи)
Категория: server
Вариации запроса: токены безопасность, ключи api хранение, интеграции безопасность
📷 Скриншоты: scr-set-20.png

**Правила.**
1. Токены/ключи (1С, A&A, service-аккаунты, X-Device-Token, CLUB_ADMIN_KEY) — только в .env/менеджере паролей; НЕ в чатах/письмах/коде.
2. Права токенов — минимально необходимые (service-аккаунт читает только нужное).
3. Ротация: при утечке/смене ответственного — немедленно.
4. Webhook-подписи (HMAC) — не отключать «для теста» в проде.
5. Доступ к .env — владелец каталога (600), группа docker под контролем (secure_install).
Контроль: аудит использования admin_access/имперсонации.

**Если не помогло:** Ескалация: «Помощь → Поддержка разработчика (MAX)».

## Физическая безопасность серверного помещения
Категория: server
Вариации запроса: серверная безопасность, доступ в серверную, физическая защита
📷 Скриншоты: scr-set-20.png

**Минимум.**
1. Сервер/свитч/ИБП — в запертом помещении/шкафу; ключи — у ответственных.
2. Доступ — журнал (кто/когда/зачем).
3. ИБП с тестами (статья hardware «ИБП»).
4. Камера/датчик в серверной (при возможности).
5. Пожарный датчик; турникеты при пожаре открываются аппаратно.
6. Температура: мониторинг/вентиляция (перегрев = сбои дисков).
Физический доступ = полный доступ: диски/BIOS не защищены от рук.

**Если не помогло:** Ескалация: «Помощь → Поддержка разработчика (MAX)».
