# visits: сценарии проходов и турникета (18 статей)

> Категория: visits-access · Полные цепочки входа/выхода по браслету/QR/лицу, регламенты и исключения.

## Полный сценарий входа по браслету
Категория: visits-access
Вариации запроса: вход по браслету сценарий, как проходит вход, цепочка турникета

**Цепочка.**
1. Клиент прикладывает браслет к считывателю турникета.
2. Контроллер читает UID → шлёт на сервер `POST /skud/checkaccess` (Basic-auth).
3. Сервер проверяет: привязка UID → клиент → активный абонемент/лимит/время/блоки → нет открытого визита.
4. Разрешено → контроллер открывает турникет + визит ACTIVE; запрещено → «Отказ» + причина в журнале.
5. Выход — аналогично (закрытие визита).
**Контроль.** Индикатор прохода в desktop (ФИО + цвет); «Входы/Выходы» — строка визита.

**Если не помогло:** Ескалация: «Помощь → Поддержка разработчика (MAX)».

## Полный сценарий входа по QR
Категория: visits-access
Вариации запроса: вход по qr сценарий, динамический qr вход, показ qr турникет

**Сценарий.**
1. Клиент: мини-приложение → «Мой QR» (динамический код, TTL `QR_TTL_MINUTES` = 2 мин на nfs, одноразовый).
2. Показывает экран сканеру турникета.
3. Сервер проверяет подпись кода (QR_SECRET_KEY) + абонемент → проход/отказ.
4. «Подпись недействительна» у всех — рассинхрон QR_SECRET_KEY (errors.md).
**Статический QR** — из «Браслеты/Карты» (постоянный, для постоянных клиентов).

**Если не помогло:** Ескалация: «Помощь → Поддержка разработчика (MAX)».

## Полный сценарий входа по Face ID
Категория: visits-access
Вариации запроса: вход по лицу сценарий, face id турникет цепочка

**Сценарий.**
1. Клиент смотрит в камеру турникета.
2. Модуль распознавания сравнивает с шаблонами (порог 0.6 по умолчанию).
3. Совпадение → проверка абонемента → проход; в журнале пометка «Face».
4. Нет шаблона/ниже порога → отказ → предложите браслет/QR.
**Условия.** Согласие на биометрию (иначе шаблонов нет), качественная регистрация лица, свет/ракурс.

**Если не помогло:** Ескалация: «Помощь → Поддержка разработчика (MAX)».

## Выход из клуба: механика
Категория: visits-access
Вариации запроса: выход из клуба, как фиксируется выход, закрытие визита

**Механика.** Карта/QR/лицо на ВЫХОДЕ → сервер закрывает визит (время выхода, длительность). Страж выхода: закрытый бесплатный шкафчик → блокировка («Откройте шкафчик №N перед выходом!»).
**Если выход не считался.** Результат: висящий визит → «409 уже в клубе» при следующем входе. Лечение: «Входы/Выходы → Завершить» с фактическим временем.

**Если не помогло:** Ескалация: «Помощь → Поддержка разработчика (MAX)».

## «Отказ» на турникете: чтение причины
Категория: visits-access
Вариации запроса: отказ причина, почему не пустил, читать отказ

**Где причина.**
1. На индикаторе прохода — краткий текст/цвет.
2. «Входы/Выходы → Отказы» — по UID: причина (нет абонемента/лимит/долг/блок/время тарифа).
3. Сервер: ответ 422 на checkaccess с detail.
**Действие сотрудника.** Открыть карточку по UID → раздел «Пакеты/Услуги»/«Блоки» → устранить причину (продление, снятие блока, оплата долга) → клиент проходит.

**Если не помогло:** Ескалация: «Помощь → Поддержка разработчика (MAX)».

## Ручной впуск/выпуск: когда и как фиксировать
Категория: visits-access
Вариации запроса: ручной впуск когда, выпуск вручную, фиксация прохода

**Когда.** Клиент без браслета (забыл/утерян), гость, технический сбой считывателя. «Входы/Выходы → 🟢 Впустить» → клиент → «OK» (способ «Ручной»).
**Фиксация.** Каждый ручной впуск — счётчик «Ручных впусков» и запись в аудите. Выпуск — «🔴 Выпустить» (с открытием турникета) или «Завершить» (без открытия).
**Регламент.** Принудительные впуски «вопреки» (нет абонемента) — только с фиксацией причины администратором.

**Если не помогло:** Ескалация: «Помощь → Поддержка разработчика (MAX)».

## Смена тарифа доступа у браслета
Категория: visits-access
Вариации запроса: сменить тариф браслета, поменять доступ, тариф доступа

**Пошагово.**
1. «Браслеты/Карты → Клиентская карта» → найти браслет.
2. Привязка хранит клиента — доступ считается по его АБОНЕМЕНТАМ, а не по «тарифу карты». Меняется покупкой/сменой абонемента клиента.
3. Если у карты был отдельный тариф доступа — правка в карточке привязки (admin).
Ожидание: турникет применяет новые условия немедленно (проверка на сервере).

**Если не помогло:** Ескалация: «Помощь → Поддержка разработчика (MAX)».

## Гостевой проход: регламент
Категория: visits-access
Вариации запроса: гостевой проход, привести друга, гость на входе

**Регламент.**
1. Карточка клиента → «ПРОЧЕЕ → Гость» → добавить гостя (ФИО/документ).
2. «Впустить» → клиент → галочка «С гостем» → выбрать гостя.
3. Оплата: гостевой тариф/услуга — платёж как обычно.
4. В журнале визит помечен «С гостем»; гость числится за клиентом.

**Если не помогло:** Ескалация: «Помощь → Поддержка разработчика (MAX)».

## Проход сотрудника: браслет/QR персонала
Категория: visits-access
Вариации запроса: проход сотрудника, вход персонала, qr сотрудника

**Схемы.**
1. Личный QR сотрудника («Браслеты/Карты → QR сотрудников»): привязан к учётке, турникет проверяет активность.
2. Браслет сотрудника — привязка как клиенту, но отметка «Сотрудник».
3. Ручной впуск — при забытых носителях (аудит).
**Увольнение.** Деактивация учётки → QR/браслет отклоняются; блокировка — на всякий случай.

**Если не помогло:** Ескалация: «Помощь → Поддержка разработчика (MAX)».

## Детский проход (ребёнок с родителем)
Категория: visits-access
Вариации запроса: ребёнок вход, детский абонемент, ребёнок с взрослым

**Регламент.** Ребёнок — отдельный клиент (своя карточка, абонемент, браслет). Вход: браслет ребёнка + сопровождающий (записывается в «Гость» родителя или отдельным визитом родителя). Доступ в зоны (бассейн/тренажёрный) — по тарифу ребёнка; сопровождение — по регламенту клуба (возрастные ограничения).

**Если не помогло:** Ескалация: «Помощь → Поддержка разработчика (MAX)».

## Турникет в ночном режиме (24/7 клубы)
Категория: visits-access
Вариации запроса: ночной режим, клуб 24/7, доступ ночью

**Настройка.** Доступ по времени — правила тарифа (время посещения). Ночной доступ — тарифы с круглосуточным временем; для ограниченных — отказ ночью (причина в журнале: «время тарифа»).
**Безопасность.** Ночью — дежурный администратор (роль с мониторингом «Входы/Выходы»), камеры, экстренная связь. Фиксируйте все отказы — попытки несанкционированного входа.

**Если не помогло:** Ескалация: «Помощь → Поддержка разработчика (MAX)».

## Антипассбек (запрет повторного входа/выхода)
Категория: visits-access
Вариации запроса: антипассбек, повторный вход запрет, двойной проход

**Ответ.** Повторный ВХОД при открытом визите → 409 «Клиент уже находится в клубе» (безопасность: карту не передать другому «внаём»). Повторный ВЫХОД без открытого визита → отказ/игнор. Ручное закрытие висящих визитов — вечерним регламентом (процессы.md «Сверка Сейчас в зале»).

**Если не помогло:** Ескалация: «Помощь → Поддержка разработчика (MAX)».

## Пропускной режим в часы пик
Категория: visits-access
Вариации запроса: очередь на входе, часы пик турникет, пропускной режим

**Рекомендации.**
1. Разделяйте вход/выход потоки (разные турникеты/направления).
2. Ресепшен с «Скан=вход» — для клиентов без браслетов (меньше очередь).
3. Динамический QR — для разовых посетителей.
4. Мониторинг «Сейчас в зале» — не превышать вместимость (безопасность).
5. Отказы в пик — оперативно: администратор у турникета с планшетом/desktop.

**Если не помогло:** Ескалация: «Помощь → Поддержка разработчика (MAX)».

## Статический QR клиента: выдача и отзыв
Категория: visits-access
Вариации запроса: статический qr выдать, отозвать qr, qr вместо браслета

**Выдача.** «Браслеты/Карты → QR клиента» → «➕» → клиент → генерация (постоянный код).
**Использование.** Клиент показывает с экрана/распечатки; турникет проверяет как карту.
**Отзыв.** «✖ Отозвать» в списке QR — код перестаёт работать (утеря телефона).
**Безопасность.** Статический QR — как ключ: не публиковать; при компрометации — отзыв + перевыпуск.

**Если не помогло:** Ескалация: «Помощь → Поддержка разработчика (MAX)».

## Face ID: свет, ракурс, очки — практические советы
Категория: faceid
Вариации запроса: face id свет, очки борода, не узнаёт советы

**Советы.**
1. Монтаж камеры: фронтальный свет, без контрового; высота 1.4–1.7 м; зона сканирования ~1 м.
2. Регистрация: анфас, без очков/капюшона, несколько кадров; повторная регистрация после смены имиджа (очки/борода).
3. Порог 0.6 стандарт; ложные пуски → 0.65–0.7; не узнаёт своих → пересъёмка + 0.55–0.6.
4. Второй фактор: лицо + браслет для чувствительных зон.

**Если не помогло:** Ескалация: «Помощь → Поддержка разработчика (MAX)».

## «Кто в зале» для эвакуации
Категория: visits-access
Вариации запроса: эвакуация кто в зале, список при пожаре, контроль выхода

**Пошагово.**
1. «Входы/Выходы → фильтр «В клубе»» — список присутствующих (время входа).
2. Сверка на выходе: все из списка — на улице.
3. Турникеты при пожарной тревоге открываются аппаратно (fire alarm) — FitIntel только показывает список.
4. После — закрыть висящие визиты («Завершить») с фиксацией в аудите.
**Регламент.** Ответственный за сверку — администратор смены; список распечатать/выгрузить.

**Если не помогло:** Ескалация: «Помощь → Поддержка разработчика (MAX)».

## Корректировка времени прохода (ошибка контроллера)
Категория: visits-access
Вариации запроса: время прохода неверное, исправить визит, сбитое время контроллера

**Почему.** Сбито время на контроллере/сервере → визиты с неверным временем.
**Пошагово.**
1. Исправьте время источника (контроллер/сервер — `timedatectl`, NTP).
2. Конкретный визит: «Завершить» с фактическим временем (ручная корректировка — в аудите).
3. Массовая ошибка — разбор с IT (перенастройка контроллера); историю не переписывать массово вручную (только через поддержку с обоснованием).

**Если не помогло:** Ескалация: «Помощь → Поддержка разработчика (MAX)».
