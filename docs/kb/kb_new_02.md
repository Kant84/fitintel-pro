## Как настроить Face ID в клубе: регистрация, камеры турникета, движок распознавания, отзыв согласия
Ключевые слова: face id, распознавание лиц, биометрия, турникет лицом, согласие 152-фз, регистрация лица, камера турникета
Формулировки вопроса: как включить распознавание лиц; турникет не узнаёт клиента; клиент не хочет face id как убрать
**Ответ.**
Face ID в FitIntel Pro: шаблон лица клиента хранится в БД, камера на турникете сравнивает в реальном времени. Два жёстких условия: согласие на биометрию (152-ФЗ, без него система отвечает 403 biometric_consent_required) и качественные кадры при регистрации. Вкладка «Face ID» в sidebar содержит 4 диалога: регистрация, камеры турникета, настройки движка, журнал.
**Сценарий 1. Включение функции и юридика.**
1. «Настройки → Параметры клуба» → включить «Обработка биометрии (152-ФЗ)». Без этого переключателя все шаги ниже недоступны.
2. Распечатайте согласие — шаблон в «Face ID → Документы».
3. Клиент подписывает; в карточке («Анкета → Согласия») ставится галочка «Биометрия».
4. Согласия хранятся как документы клиента — скан подшивается в «Документы» карточки.
**Сценарий 2. Регистрация лица клиента.**
1. «Face ID → Регистрация» → поиск клиента по ФИО/телефону.
2. «Начать захват». Клиент смотрит в камеру: расстояние 40–70 см, лицо анфас, равномерный свет.
3. «Захват» — кадр. Сделайте 3–5 захватов с поворотом головы ±15°: разнобой кадров повышает точность на турникете.
4. «Сохранить шаблон». Успех — статус «Лицо зарегистрировано».
5. Клиентам в очереди регистрируйте в непиковые часы и просите снять очки/капюшон.
**Сценарий 3. Камеры турникета и движок.**
1. «Face ID → Камеры турникета» → «Добавить»: RTSP-адрес камеры, зона прохода, направление (вход/выход).
2. Проверка RTSP: откройте строку подключения в VLC с того же ПК — если VLC не видит, камеру надо чинить до настройки.
3. «Face ID → Настройки движка»: порог уверенности 0.8 — стандарт. 0.75 — если зарегистрированные массово не узнаются; выше 0.85 — если проходят посторонние.
4. Тест: зарегистрированный клиент проходит → «Входы/Выходы» визит с пометкой Face ID.
**Сценарий 4. Отзыв согласия (обязательный по 152-ФЗ).**
1. Клиент попросил удалить данные: карточка → «Прочее → Биометрия → Удалить шаблон».
2. Зафиксируйте дату отзыва; журналирование — «Face ID → Журнал».
**Проверка.**
- «Face ID → Журнал»: события «распознан/отказ» с кадром и временем, совпадают с реальными проходами.
- Клиент со согласием проходит; без согласия система его «не видит».
**Возможные ошибки.**
- 403 biometric_consent_required — нет галочки согласия в карточке клиента.
- «Камера не найдена» — RTSP недоступен: VLC-тест, сеть, питание камеры.
- «Лицо занято» — шаблон уже привязан к другому клиенту: найдите дубль базы, удалите лишний.
- Ошибка 500 в разделе «лицо» — пересохраните «Service-аккаунты» в «Настройках».
**FAQ.**
- Работает в тёмном коридоре? Только с подсветкой камеры — контровой свет убивает распознавание.
- Очки/маска влияют? Да: регистрируйте без аксессуаров, шаблон с ними слабый.
**Если не помогло:** «не помогло» + шаг и текст из «Face ID → Журнал».

## Как подключить и запустить вендинг-автомат: регистрация, оплата кодом и браслетом, журнал продаж
Ключевые слова: вендинг, автомат, торговый автомат, оплата кодом, оплата браслетом, mdb, журнал автомата, склад автомата
Формулировки вопроса: как настроить автомат с едой; клиент оплатил автомат а товар не выдал; вендинг не списывает с браслета
**Ответ.**
Вендинг в FitIntel Pro — вкладка «Магазин» (sidebar). Автомата два способа оплаты: **кодом** (клиент показывает QR на экране автомата — списание с баланса) и **браслетом** (поднесение к считывателю автомата). Контракт с автоматом — по протоколу MDB; регистрация автомата — с X-Device-Token; каждая продажа требует подтверждения (confirm) — без него операция висит.
**Сценарий 1. Регистрация автомата.**
1. «Магазин» → «Оборудование» → «Добавить автомат».
2. Заполните: название (например, «Снеки, 2 этаж»), точку установки, тип контракта (MDB).
3. Сгенерируйте X-Device-Token — он уникален на автомат; запишите в контроллер автомата (поле токена в прошивке/приложении контроллера).
4. «Проверка связи» — статус автомата «онлайн». Не онлайн: сеть автомата, порт, токен.
5. Привяжите складскую точку: «Магазин → Склад» — списания будут уходить с её остатков.
**Сценарий 2. Оплата кодом (QR).**
1. Клиент у автомата выбирает товар → автомат показывает QR.
2. QR содержит сумму и id операции; срок жизни кода — ограничен (параметр клуба).
3. Клиент сканирует QR из MAX-клиента клуба (или показывает его на ресепшене) — списание с баланса.
4. Автомат получает confirm → выдаёт товар. Без confirm продажа висит в «ожидает подтверждения».
5. Если код протух — автомат генерирует новый; старый ничего не спишет.
**Сценарий 3. Оплата браслетом.**
1. Считыватель автомата привязан к контракту MDB: поднесение браслета = авторизация суммы.
2. Списание — с внутреннего баланса клиента; при нулевом балансе автомат откажет с сигналом.
3. Каждая продажа — строка в «Магазин → Журнал»: время, браслет/id, сумма, статус.
**Проверка.**
- Тестовая покупка кодом и браслетом: товар выдан, баланс списан, журналная строка со статусом «завершено».
- Остатки склада уменьшились на выданный товар.
**Возможные ошибки.**
- «Автомат не отвечает» — неверный X-Device-Token или автомат офлайн: проверьте токен и связь.
- Продажа висит без confirm — контроллер не дождался подтверждения: журнал → «Подтвердить» вручную; товар при этом уже выдан — сверьте фактическую выдачу.
- Списалось дважды — двойной confirm: одну операцию отмените через журнал (возврат).
**FAQ.**
- Можно автомат без контроллера MDB? Нет — только MDB-контракт.
- Комиссия автомата? В настройках контракта указывается, в отчётах — отдельной строкой.
**Если не помогло:** «не помогло» + номер операции из «Магазин → Журнал».

## Как работать с RFID-браслетами: запись с нуля, перевыпуск при потере, сброс и аппаратные ошибки
Ключевые слова: браслет, rfid, mifare, записать браслет, перевыпуск, потерял браслет, acr1252, сброс браслета, карта уже записана
Формулировки вопроса: как запрограммировать браслет; браслет не пищит на турникете; клиент потерял браслет что делать
**Ответ.**
Браслеты — MIFARE, записываются со считывателя ACR1252 (вкладка «Браслеты/Карты»). Связка: браслет ↔ карточка клиента; проход — по турникету или доски раздевалок. Ниже три сценария: запись нового, перевыпуск при потере, сброс битого браслета.
**Сценарий 1. Записать браслет (MIFARE) с нуля.**
1. Вкладка «Браслеты/Карты» → «Программирование» → «Носитель» → «MIFARE браслет».
2. Поднесите браслет к ACR1252 — считыватель пикнул, браслет опознан.
3. «Записать карту». Ожидание: статус «Записано», считыватель пикает 2 раза.
4. Если «Карта уже записана» — браслет бывший в обороте: пропустите шаг (сброс не нужен, если данные корректны) или сделайте «Сброс/перевыпуск».
5. Ошибка «Не удалось записать: <причина>» — карта не MIFARE (чужой формат), битый сектор или порт считывателя занят: смените браслет/порт.
6. После записи привяжите к клиенту: поиск карточки → «Браслеты → Привязать» → поднесите браслет ещё раз.
7. Тест: турникет пускает; в «Входы/Выходы» визит с браслетом.
**Сценарий 2. Перевыпуск при потере.**
1. Карточка клиента → «Прочее → Блоки» → «Заблокировать старый браслет» (стоп-лист турникета, мгновенно).
2. «Браслеты/Карты» → «Перевыпуск» → новый браслет → запись по сценарию 1.
3. Старый браслет при находке не оживёт — он в стоп-листе.
4. Если браслет был ещё и кошельком — баланс переходит на новый автоматически (привязка к клиенту, не к носителю).
**Сценарий 3. Сброс браслета.**
1. «Браслеты/Карты» → «Сброс» → поднесите браслет.
2. Ожидание: «Носитель очищен». После сброса браслет как новый (сценарий 1).
**Проверка.**
- Каждый новый браслет: тестовый проход через турникет до выдачи клиенту.
- Список активных носителей клиента — один активный браслет, старые в стоп-листе.
**Возможные ошибки.**
- Считыватель не видит браслет: порт занят другим приложением (закройте лишние), USB-переподключение ACR1252.
- «Карта уже записана» — см. п.4 сценария 1.
- Турникет пищит, но не пускает: браслет не привязан (шаг 6) или блокировка стоп-листом.
**FAQ.**
- Браслет клиента можно копировать? MIFARE с записью защищён сектором — копия не пройдёт на турникете.
**Если не помогло:** «не помогло» + текст ошибки записи и модель считывателя.

## Как восстановить работу сервера клуба после сбоя: бэкапы, откат, проверка целостности
Ключевые слова: бэкап, восстановление, откат, сбой сервера, база данных, репликация, аварийное восстановление
Формулировки вопроса: сервер умер как поднять; как откатить базу; проверить бэкапы
**Ответ.**
Архитектура: сервер клуба (VM) + Docker-контейнеры (api/db/nginx) + ежедневные бэкапы БД + выносная копия (offsite). Восстановление = поднять контейнеры + залить последний бэкап + проверить. Регламент ниже — для аварий и для учебных откатов.
**Сценарий 1. Контроль бэкапов (делать до сбоя).**
1. Ежедневный бэкап: скрипт `install_cron.sh` ставит задачу; каталог бэкапов — вне контейнера.
2. Выносная копия: на отдельную машину (по регламенту — сервер 125) — раз в сутки.
3. Раз в месяц: учебное восстановление на тестовом стенде — бэкап, который не восстанавливается, равен его отсутствию.
**Сценарий 2. Аварийное восстановление.**
1. Оцените сбой: контейнеры упали (`docker compose ps`) — перезапуск; диск/VM мертвы — переустановка.
2. Переустановка: git clone репозитория → `.env` (из сохранённой копии — пароли не в git!) → `install_prod.sh`.
3. Бэкап БД: последний файл из каталога бэкапов → восстановление в postgres-контейнер.
4. Подъём: `docker compose up -d` → ожидание healthcheck БД.
5. Проверка: `/health` отвечает, desktop подключается («Сервер подключён»), логин суперадмина работает.
**Сценарий 3. Точечный откат (удалили лишнее).**
1. Найдите бэкап до операции (по времени).
2. Восстановите на ТЕСТОВЫЙ стенд, выгрузите нужные данные (SQL) — не откатывайте прод целиком ради одной таблицы.
3. Вставьте выгрузку в прод ручной правкой или через поддержку.
**Проверка после восстановления.**
- Число клиентов/платежей за вчера сходится с бумажными/эквайринговыми источниками.
- Лицензия активна («Настройки → Лицензия»); если слетела — повторная активация ключом.
**Возможные ошибки.**
- Бэкапы пустые/мелкие — место на диске закончилось: контроль свободного места в ежедневный чек-лист.
- «password authentication failed» после восстановления — .env не тот: сверьте с сохранённой копией.
- Контейнеры в рестарте — порт занят/конфликт сети: `docker compose down && up -d`, логи.
**FAQ.**
- Как часто бэкапится? Ежедневно автоматически; критичные периоды (переезд базы) — ручной бэкап перед работами.
**Если не помогло:** «не помогло» + на каком шаге и вывод `docker compose ps`.

## Как настроить права сотрудников клуба: матрица ролей, счётчики прав, типовая схема на 10 человек
Ключевые слова: роли, права, rbac, пользователи, доступ, матрица ролей, 12 ролей, счётчики прав, добавить сотрудника
Формулировки вопроса: кто что может в программе; как завести нового админа; сотрудник не видит кнопку; выдать права кассиру
**Ответ.**
В FitIntel Pro 12 ролей (sidebar «Пользователи»): Superadmin, Admin, Manager, Cashier, Accountant, Trainer, Reception, Client, Client demo, Security SKUD, Platform support, Owner. Права — флаги (счётчики фактические: Superadmin 75, Manager 19, Cashier 11, Accountant 8, Trainer 4, Client 8). Карточка сотрудника — график, документы (шифрование AES-256-GCM), «Матрица ролей» показывает эффективные права.
**Сценарий 1. Завести сотрудника.**
1. «Пользователи» → «Добавить пользователя»: ФИО, логин, пароль (сложный, 12+ символов), роль.
2. «Документы» — трудовой договор/согласие на ПДн (шифруются автоматически).
3. «График» — смены сотрудника (для зарплаты и отметок).
4. Тестовый вход сотрудником: видит только свои вкладки.
**Сценарий 2. Типовая схема на 10 человек.**
1. Директор — Superadmin (75 прав, всё).
2. Администратор смены — Manager (19: клиенты, продажи, расписание; без зарплат и настроек).
3. Два кассира — Cashier (11: платежи, касса, чеки).
4. Бухгалтер — Accountant (8: бухгалтерия, выгрузки, зарплата).
5. Три тренера — Trainer (4: расписание, свои клиенты, отметки занятий).
6. Ресепшен — Reception (приём, браслеты, визиты).
7. Охрана — Security SKUD (входы/выходы, турникет).
8. Все — свой логин; общих учёток не создавать (аудит действий по пользователю).
**Сценарий 3. Сотрудник не видит кнопку/вкладку.**
1. Проверьте роль: карточка сотрудника → «Матрица ролей» — есть ли флаг на нужный экран.
2. Нет флага — смена роли или выдача отдельного права владельцем.
3. Есть флаг, но вкладки нет — перелогин: права применяются при входе.
**Проверка.**
- «Экраны ролей» («Настройки») — кто какие экраны видит.
- Аудит: «История» — действия сотрудников по пользователю.
**Возможные ошибки.**
- 400 на roles/assign — кривой email/логин сотрудника: проверьте формат.
- 500 users — редкий бэкенд-баг: пересоздание пользователя; логи в «История».
**FAQ.**
- Можно ли кастомную роль? Права настраиваются по флагам в карточке роли — типовых 12 достаточно для любой схемы.
**Если не помогло:** «не помогло» + логин сотрудника и какой экран не виден.
